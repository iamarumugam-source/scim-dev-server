SCIM Dev Server — UX proposals

Mockups for the findings from the UI review. Each shows the current behaviour against a proposal. Nothing here is wired up — it is a static reference for deciding what to build.

1 · Users table has no search

The highest-impact gap. Users paginate server-side at 30 rows per page, so with the mock generator now capable of 5000 users that is 167 pages with no way to jump to a specific person. The API already supports ?filter=userName eq "…", so the server side exists.

Adds: debounced search bound to the existing SCIM filter, sortable columns, a status facet, and ⌘K to focus. Row count updates to reflect the query.
One caveat to design around. The server filter only supports userName eq "…" — exact match on a single attribute, and it truncates the value at @. A search box implies substring matching, so either the filter needs a co (contains) branch server-side, or the box should be labelled “Find by username” to set the right expectation. Shipping a search box over an exact-match backend will read as broken.

2 · No bulk actions

Test data is disposable by nature, but users can only be deleted one row at a time through a per-row menu. After generating 500 users, trimming them down is impractical.

3 · Empty states are mostly missing

A fresh tenant shows an empty table with “No results found”, which does not tell a first-time user what to do. The single most useful action — generate mock data — lives in the sidebar, away from where the user is looking.

Smaller findings

  • /icon-preview is publicly reachable. The middleware matcher only covers /scim/* and /meeting-planner/*, so this 373-line design scratch page is served to anyone without login. Either protect it or delete it.
  • Dead file. src/app/users/data-table.tsx is orphaned — src/app/users/page.tsx is a 5-line redirect that never imports it.
  • Generate Mock lives in the sidebar. A large form with seven fields sits inside the navigation component, which is part of why app-sidebar.tsx is 742 lines. It also makes the app's most useful first action hard to find. Moving it into the empty state and/or a page-level action would help discovery and shrink the component.
  • src/app/scim/page.tsx is 960 lines. The dashboard mixes data fetching, aggregation and every tile in one file — the kind of file where a bug like the 1000-row user count hides.
  • No visible rate-limit feedback. Tenants are capped at 60 req/min and a breach returns 429, but the UI gives no indication before or when it happens. A quiet indicator on the dashboard would explain otherwise-mysterious failures.
